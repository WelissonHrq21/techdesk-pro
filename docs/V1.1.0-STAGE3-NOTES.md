# TechDesk Pro v1.1.0 - Stage 3 Notes

## Scope

Stage 3 implements the frontend experience for auditable reversal of stock consumed during service-order maintenance.

Included:

- Service order detail displays original `EXIT` consumptions.
- Linked `REVERSAL` movements are displayed under the original consumption.
- The UI shows consumed, reversed, net consumption, and reversible balance.
- `ADMIN` and `TECHNICIAN` can reverse eligible consumption.
- `RECEPTION` can view consumption history but cannot reverse it.
- Reversal form validates quantity and reason before calling the API.
- Stale data conflicts return a friendly 409 message, refetch the OS, and keep the session alive.
- 403 errors are shown without logging the user out.
- Frontend tests cover role, status, validation, partial reversal, full reversal, 409, 403, and REVERSAL rendering.

Not included:

- Backend behavior changes.
- `Customer.document`.
- `AppSettings`.
- Installer/setup changes.

## API Client

The frontend now uses:

```http
POST /stock-movements/:id/reverse
```

Request body:

```json
{
  "quantity": 1,
  "reason": "Peça não será utilizada"
}
```

The API call is centralized in `serviceOrdersApi.ts` through `reverseStockMovement`.

## Types

`StockMovementType` now includes:

- `REVERSAL`.

Service-order stock movements now expose:

- `partId`.
- `serviceOrderId`.
- `userId`.
- `reversalOfMovementId`.

The reversal response exposes:

- `reversedQuantity`.
- `reversibleQuantity`.
- `movement.reversalOfMovement`.

## Service Order UI

The service-order detail screen now separates:

- Original `EXIT` movement.
- Linked `REVERSAL` movements.
- Gross consumed quantity.
- Already reversed quantity.
- Net consumed quantity.
- Reversible balance.

The original `EXIT` remains visible after partial or full reversal. `REVERSAL` movements are added as separate audit entries, preserving the stock history instead of rewriting the original consumption.

The maintenance approved/consumed summary also shows reversed and net consumption values per part.

## Reversal Action

The `Estornar` action appears only when all frontend conditions are true:

- User role is `ADMIN` or `TECHNICIAN`.
- Service order status is `IN_MAINTENANCE` or `FINISHED`.
- Movement is an original service-order `EXIT`.
- Reversible quantity is greater than zero.

The action does not appear for:

- `RECEPTION`.
- `DELIVERED`.
- Movements already fully reversed.

## Reversal Form

The modal shows:

- Part name.
- Original consumed quantity.
- Already reversed quantity.
- Net consumption.
- Available quantity for reversal.

Validation:

- `quantity` is required.
- `quantity` must be an integer.
- `quantity` must be at least `1`.
- `quantity` cannot exceed `reversibleQuantity`.
- `reason` is required after trim.
- `reason` is limited to 500 characters.

The form informs the user that the original consumption is preserved, stock is returned, and the reversal is recorded in history.

## Cache Invalidations

After a successful reversal, the frontend invalidates:

- `["service-orders"]`.
- `["service-order", serviceOrderId]`.
- `["dashboard", "summary"]`.
- `["parts"]`.
- `["part", partId]`.
- `["stock-movements", partId]`.

This refreshes the OS detail, lists, dashboard cards, part stock, and stock movement history.

## Error Handling

409 conflict:

- Shows a friendly stale-data message.
- Refetches the service order.
- Does not log out the user.

403 forbidden:

- Shows a friendly permission message.
- Preserves the authenticated session.

## Risks

- The backend consumption rule still calculates consumed quantity from gross `EXIT` movements. The frontend therefore keeps the existing gross consumed value for deciding whether another approved-budget consumption can be opened, while separately displaying reversed and net values. This avoids showing an action that the backend would reject.
- Stage 3.1 later corrected this backend risk by making operational consumption use net consumed quantity.
- Browser-based manual smoke was not performed against a live pilot database to avoid changing real pilot data during this frontend task.
