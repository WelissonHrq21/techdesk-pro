# TechDesk Pro v1.2.0 - Stage 6 Notes

## Scope and decision

Stage 6 adds a secure QR Code for the existing public service-order tracking
route and closes the v1.2.0 functional scope. No backend, schema, migration,
installer, workflow or release-pipeline change was required.

The QR is printed on both the service-order receipt and the budget. Reusing it
on the budget was selected because the same small component fits the existing
A4 layout without duplicating business logic or adding another endpoint.

## QR and URL strategy

The QR payload contains only:

`<current browser origin>/track/<publicToken>`

`buildPublicTrackingUrl` is the single URL builder used by the QR, the internal
open action and the copy action. It uses `window.location.origin`, preserves the
current HTTP or HTTPS scheme and does not persist an installation IP. URLs
printed after a LAN, hostname, port, proxy or network-mode change therefore use
the origin through which the operator currently accesses TechDesk Pro.

The helper was verified with localhost, a LAN address, a hostname and HTTPS.
There is no hardcoded localhost, private IP or forced HTTP in production code.
No `trust proxy` change is needed because generation happens in the browser.

The existing UUID `ServiceOrder.publicToken` is reused. The QR does not contain
customer, equipment or internal service-order IDs, CPF/CNPJ, diagnosis, stock,
password, JWT, query parameters or secrets. Invalid tokens keep returning a
safe HTTP 404. Public tracking remains available for cancelled and delivered
orders according to the existing policy.

## Library and rendering

Dependency: `qrcode.react` 4.2.0.

- SVG output for sharp print rendering;
- 120 x 120 CSS pixels, approximately 32 mm at 96 dpi;
- error correction level `M`;
- quiet margin of two modules;
- no runtime dependency tree beyond the React peer dependency;
- accessible SVG title and `aria-label`;
- visible instructions and a textual, selectable URL below the QR.

The QR block uses a stable size and avoids breaking internally across printed
pages. The receipt and mixed-budget A4 layouts were visually checked at an
820-pixel document width with no horizontal overflow. Signatures, item table,
totals and approval fields remained visible.

## Internal and public experience

The service-order workspace now provides `Abrir tracking` and `Copiar link`
using the same URL helper. Successful copy shows `Link copiado.`

The mobile public page was validated at 390 x 844 pixels. The content width was
358 pixels with no horizontal overflow and no private terms visible.

Visual testing also found and fixed a stale-session edge case: a revoked JWT in
local storage could redirect a public tracking visitor to login while `/me` was
being restored. The session is now cleared without leaving `/track/:token`.
Private routes keep their existing redirect-to-login behavior.

## Security and privacy

The backend was not changed. Existing protections remain active:

- public responses select only number, status, dates and basic equipment data;
- invalid tokens return 404 without stack, Prisma or SQL details;
- request logs replace the public token path with
  `/public/service-orders/:token`;
- Authorization headers remain redacted;
- the QR payload is not logged by the frontend.

Public tracking is independent of JWT and `tokenVersion`. OpenAPI already
documents the existing public endpoint correctly, so no API contract update or
QR endpoint was added.

## Limitations and cuts

- QR generation is intentionally browser-side; server-generated emails or PDFs
  would need an explicit configured public origin in a future release.
- Previously printed paper naturally keeps the origin printed at that time;
  newly printed documents always follow the current browser origin.
- No QR was added to the internal screen because open and copy actions already
  cover that workflow without visual noise.
- No dashboard, reports, SKU, installer, manager or supply-chain work entered
  this stage.

## Feature freeze

The v1.2.0 functional scope is frozen after Stage 6. New COULD items are deferred
unless they address a release blocker. The next stage is RC and release
validation.
