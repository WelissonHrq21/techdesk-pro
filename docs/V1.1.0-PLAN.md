## 2. Objetivos

A v1.1.0 deve ser uma evolucao compativel, orientada pelo piloto real, sem reescrever a base v1.0.0.

Objetivos principais:

- Evoluir a experiencia de instalacao para um setup mais automatizado, seguro e amigavel, sem descartar a base validada do installer v1.0.0.
- Corrigir uma lacuna operacional real no estoque: estorno auditavel de consumo de peca.
- Reduzir duplicidade de cliente com documento opcional e normalizado.
- Planejar onboarding web de primeiro acesso para configurar dados funcionais do produto sem expor secrets de infraestrutura.
- Avaliar melhoria de bundle sem transformar a versao em sprint de performance.
- Manter JWT/localStorage como esta em v1.1.0, documentando a migracao para cookies HttpOnly como hardening futuro.

### 4.4 Estrategia JWT

Origem: ADR-023/024.

Problema: `localStorage` aumenta impacto de XSS; troca de senha nao revoga JWT ja emitido.

Comparacao:

| Modelo | Beneficios | Riscos/custos |
| --- | --- | --- |
| JWT bearer em localStorage atual | Simples, ja validado, funciona com API e frontend atuais | Token acessivel em XSS, sem revogacao ativa |
| Cookie HttpOnly/Secure/SameSite | Reduz exposicao do token ao JS, combina com same-origin | Exige novo contrato de auth, CSRF, CORS/credentials, logout diferente, testes e hardening maior |

Classificacao:

| Criterio | Avaliacao |
| --- | --- |
| Valor operacional | Medio |
| Risco | Alto |
| Esforco | Alto |
| Impacto no banco | Pequeno a significativo se houver sessao/tokenVersion |
| Impacto na API | Significativo |
| Impacto no frontend | Significativo |
| Impacto em seguranca | Significativo |
| Prioridade | NOT NOW |

Recomendacao: nao entrar na v1.1.0. Planejar para sprint de hardening, possivelmente v1.2.0, com `tokenVersion` ou tabela de sessoes.

Motivo: maior lacuna operacional identificada apos v1.0.0. Afeta estoque, OS, auditoria e confianca do tecnico.

Escopo:

- Criar movimento inverso auditavel.
- Preservar movimento original.

- Permitir estorno parcial e total.

### 7.2 Documento opcional do cliente

Motivo: reduz duplicidade sem quebrar clientes existentes.

Escopo:

- Campo opcional e unico quando preenchido.
- Suportar CPF e CNPJ por campo generico `document`.
- Armazenar apenas digitos em `document`.
- Validar CPF/CNPJ no frontend e backend quando informado.
- Incluir em busca de clientes.
- Mostrar em detalhe/listagem de cliente onde fizer sentido.

### 7.3 Code splitting por rota

Motivo: melhoria simples, evidencia objetiva de bundle > 500 kB, baixo risco se feita com `React.lazy`/`Suspense`.

- Nao trocar bibliotecas nem redesenhar telas.

## Installer / Setup Experience

### Principio arquitetural

Separar duas responsabilidades:

```text
Installer / Bootstrapper
  -> infraestrutura, Docker, Compose, imagens, env, secrets, porta, health, logs

TechDesk Web / Onboarding
  -> empresa, administrador, usuarios iniciais, preferencias e orientacao operacional
```

Secrets de infraestrutura como `POSTGRES_PASSWORD` e `JWT_SECRET` nunca devem ser configurados ou exibidos pela interface web comum.

### Alternativa A - Bootstrapper/script aprimorado

Base: `deploy/install.sh`, `deploy/install.ps1`, Compose e imagens GHCR ja existentes.

Pontos fortes:

- Evolucao incremental da base validada em v1.0.0.
- Baixa complexidade.
- Facil manutencao junto do repositorio.
- Funciona bem em Ubuntu Server com Docker Engine.
- Permite logs textuais simples e diagnosticos claros.
- Gera env/secrets localmente sem expor ao frontend.
- Pode ser empacotado em ZIP ou release asset baixavel.

Pontos fracos:

- Experiencia menos amigavel que uma UI grafica.
- Windows depende de PowerShell, Docker Desktop/WSL2 e configuracao local.
- Usuario ainda precisa abrir terminal, ao menos na primeira versao.

Recomendacao: usar primeiro na v1.1.0.

### Alternativa B - Installer grafico

Possibilidades futuras:

- Aplicacao desktop pequena que orquestra Docker/Compose.
- Wrapper nativo por plataforma.
- UI web local temporaria servida pelo bootstrapper.

Pontos fortes:

- Melhor experiencia visual.
- Pode exibir etapas, progresso e erros com mais clareza.
- Facilita "Abrir TechDesk Pro" apos instalacao.

Pontos fracos:

- Aumenta superficie de manutencao e seguranca.
- Pode exigir runtime, assinatura, atualizacoes do proprio installer e permissao administrativa.
- Em Windows, Docker Desktop/WSL2/licenciamento/virtualizacao tornam suporte oficial mais caro.
- Em Linux server, UI grafica pode ser inadequada.

Recomendacao: nao iniciar por installer grafico na v1.1.0. Desenhar caminho, mas entregar bootstrapper robusto primeiro.

### Plataforma suportada

Decisao proposta:

- Plataforma oficial de servidor v1.1.0: Linux/Ubuntu Server com Docker Engine + Compose.
- Windows: manter scripts e documentacao como melhor esforco para laboratorio/pequenas instalacoes, mas nao prometer como servidor oficial ate validar Docker Desktop/WSL2, reboot, firewall, backup, atualizacao e disponibilidade.

### Nova instalacao

Fluxo desejado:

```text
verificar ambiente
verificar Docker/Compose
verificar internet
escolher porta
gerar secrets
criar .env com permissao adequada
baixar imagens oficiais versionadas
subir postgres
aplicar migrations
subir API/frontend
validar health/ready
mostrar URL
abrir TechDesk/onboarding
orientar backup inicial
```

### Rerun e idempotencia

O bootstrapper deve detectar instalacao existente por:

- `.env` existente.
- `TECHDESK_PROJECT_NAME`.
- containers do Compose.
- volume `techdesk_pgdata` do projeto.
- banco respondendo.

Rerun deve:

- preservar `.env`;
- preservar secrets;
- nao recriar volume;
- nao resetar ADMIN;
- nao rodar operacao destrutiva;
- oferecer `status`, `repair` ou `upgrade` conforme o caso.

### Install, Upgrade e Repair

Responsabilidades:

- `install`: nova instalacao sem volume/config existente.
- `upgrade`: backup, validacao, trocar imagens versionadas, migrations, health, smoke e plano de rollback.
- `repair`: diagnosticar e tentar corrigir problema nao destrutivo, como container parado, imagem ausente, porta em conflito ou config incompleta.

Limites:

- Nenhum modo normal executa `down -v`, remove volume, reseta banco ou troca secrets silenciosamente.
- Restore real continua procedimento controlado fora de botao simples.

### Logs

Logs do installer devem conter:

- etapa;
- horario;
- comando/servico afetado;
- resultado de healthcheck;
- erro sanitizado;
- sugestao de proxima acao.

Nunca registrar:

- `JWT_SECRET`;
- `POSTGRES_PASSWORD`;
- senha ADMIN;
- token Bearer;
- URL com token publico completo.

### Distribuicao baixavel

Caminho recomendado:

```text
GitHub Release
  -> TechDesk-Pro-Setup-vX.Y.Z.zip
  -> checksum SHA256
  -> instrucoes curtas
  -> imagens GHCR versionadas
```

Assinatura de executavel pode ser avaliada quando houver installer grafico. Para v1.1.0, checksum e versionamento explicito sao suficientes.

## 10. Modelagem Proposta

### 10.1 Estorno auditavel

Alteracao conceitual:

```prisma
enum StockMovementType {
  ENTRY
  EXIT
  ADJUSTMENT
  REVERSAL
}

model StockMovement {
  id       String            @id @default(uuid())
  type     StockMovementType
  quantity Int
  reason   String?

  createdAt DateTime @default(now())

  partId String
  part   Part   @relation(fields: [partId], references: [id])

  serviceOrderId String?
  serviceOrder   ServiceOrder? @relation(fields: [serviceOrderId], references: [id])

  userId String?
  user   User?   @relation(fields: [userId], references: [id])

  reversalOfMovementId String?
  reversalOfMovement   StockMovement?  @relation("StockMovementReversal", fields: [reversalOfMovementId], references: [id])
  reversals            StockMovement[] @relation("StockMovementReversal")

  @@index([partId])
  @@index([serviceOrderId])
  @@index([createdAt])
  @@index([reversalOfMovementId])
}
```

Regras:

- `REVERSAL` sempre incrementa estoque.
- `REVERSAL.reversalOfMovementId` aponta para um `EXIT` de consumo de OS.
- O `partId` e `serviceOrderId` do estorno devem ser iguais aos do movimento original.
- A soma de `REVERSAL.quantity` para um `EXIT` nao pode exceder `EXIT.quantity`.
- Motivo deve ser obrigatorio.
- Estorno parcial e total sao permitidos.
- Estorno nao deve apagar nem editar o movimento original.

Estados da OS:

- Permitido: `IN_MAINTENANCE` e `FINISHED`.
- Nao permitido diretamente: `DELIVERED`.
- Nao recomendado: `CANCELLED`.

Decisao: permitir estorno parcial e total em `IN_MAINTENANCE` e `FINISHED`. Se for necessario corrigir estoque de uma OS entregue, criar no futuro um fluxo explicito de reabertura/correcao, nao uma excecao escondida.

## 11. API Proposta

### 11.1 Estorno de consumo

Novo endpoint:

```text
POST /stock-movements/:id/reverse
```

Alternativa aceitavel:

```text
POST /service-orders/:serviceOrderId/stock-movements/:movementId/reverse
```

Recomendacao: usar `POST /stock-movements/:id/reverse`, pois a entidade estornada e o movimento.

Request:

```json
{
  "quantity": 1,
  "reason": "Peca nao sera utilizada"
}
```

Response:

```json
{
  "part": { "id": "...", "stock": 2 },
  "movement": {
    "id": "...",
    "type": "REVERSAL",
    "quantity": 1,
    "reason": "Peca nao sera utilizada",
    "reversalOfMovementId": "..."
  }
}
```

RBAC:

- `ADMIN`: permitido.
- `TECHNICIAN`: permitido enquanto OS estiver em estado permitido.
- `RECEPTION`: negado.

Erros esperados:

- `404`: movimento original nao encontrado.
- `400`: movimento nao e `EXIT`, nao possui OS, OS em status invalido, motivo ausente.
- `409`: quantidade de estorno excede saldo reversivel.
- `403`: role sem permissao.

Idempotencia:

- Nao usar idempotencia implicita por request repetido.
- A protecao principal e saldo reversivel por movimento original.
- Opcional futuro: chave idempotente no header para integracoes.

Endpoints alterados:

- `GET /parts/:id/stock-movements`: incluir `reversalOfMovementId` e, se util, `reversedQuantity`.
- `GET /service-orders/:id`: incluir movimentos `REVERSAL` em `stockMovements`.
- OpenAPI deve documentar `REVERSAL`.

Endpoints inalterados:

- `POST /service-orders/:id/parts/:partId/consume`
- `POST /parts/:id/stock/entry`
- `POST /parts/:id/stock/exit`

### 11.2 Documento do cliente

Endpoints alterados:

- `POST /customers`
- `PUT /customers/:id`
- `GET /customers`
- `GET /customers/:id`

Request create/update:

```json
{
  "name": "Cliente",
  "phone": "11999999999",

}
```

## 15. Migration

Plano de migration v1.0.0 -> v1.1.0:

1. Adicionar enum value `REVERSAL` em `StockMovementType`.
2. Adicionar `reversalOfMovementId` nullable em `StockMovement`.
3. Criar foreign key autorreferenciada.
4. Criar index em `reversalOfMovementId`.
5. Adicionar `Customer.document` nullable.
6. Criar unique constraint/index para `Customer.document`.
7. Adicionar singleton de setup, preferencialmente `AppSettings`, com `setupCompleted` e `setupCompletedAt`.

Compatibilidade:

- Todos os `StockMovement` existentes continuam validos.
- Clientes existentes ficam com `document = null`.
- Dados de OS, budgets, users, histories, company settings e parts devem ser preservados.
- Reversals antigos nao existem, portanto nao ha backfill.
- Instalacoes v1.0.0 existentes devem receber `setupCompleted = true` ou estrategia equivalente durante upgrade, para nao reabrir onboarding em producao ja configurada.

Risco:

- Alterar enum PostgreSQL precisa ser testado no upgrade real.
- Unique em documento e seguro porque a coluna inicia nullable, mas deve ser validado em banco com dados reais.

## 18. Riscos

Riscos principais:

- Estorno concorrente duplicado causar estoque incorreto.
- Regra de estorno em `FINISHED` precisa ficar clara para nao virar correcao escondida apos entrega.
- Documento CPF/CNPJ criar expectativa legal/fiscal maior do que o produto suporta.
- Documento sensivel aparecer em lugar indevido, principalmente tracking publico ou logs.
- Installer sobrescrever env/secrets ou volume em rerun.
- Installer grafico prematuro aumentar complexidade sem maturidade operacional.
- Onboarding abrir superficie de criacao indevida de ADMIN.
- Bundle splitting quebrar rotas protegidas se feito sem testes.
- Migration de enum PostgreSQL precisa ser validada no upgrade real.

Mitigacoes:

- Usar transacao para calcular saldo reversivel e criar movimento.
- Estorno permitido apenas em `IN_MAINTENANCE` e `FINISHED`; `DELIVERED` exige fluxo futuro explicito.
- Documento opcional, normalizado e nao exposto publicamente.
- Bootstrapper idempotente, logs sanitizados e modos separados para install/upgrade/repair.
- Onboarding protegido por estado de setup e/ou login ADMIN quando aplicavel.
- Testes de API, frontend, installer e upgrade.

## 21. Respostas Obrigatorias

1. Qual arquitetura recomenda para o instalador da v1.1?
   - Recomendo uma arquitetura em duas camadas: bootstrapper/installer cuidando de infraestrutura e TechDesk Web/Onboarding cuidando de configuracao funcional. O frontend normal nunca deve configurar ou exibir secrets como `POSTGRES_PASSWORD` e `JWT_SECRET`.

2. Devemos comecar por bootstrapper/script ou installer grafico?
   - Comecar por bootstrapper/script aprimorado, evoluindo `install.sh`, `install.ps1`, Compose, logs, validacoes e empacotamento baixavel.

3. Um installer grafico ja e justificavel na v1.1?
   - Nao como primeira entrega. Ele deve ficar desenhado no roadmap futuro, pois adiciona manutencao, seguranca, assinatura, runtime, privilegios e complexidade por plataforma.

4. Linux deve continuar sendo a plataforma oficial de servidor?
   - Sim. A plataforma oficial recomendada para servidor v1.1 e Linux/Ubuntu Server com Docker Engine + Compose, porque foi a base validada na v1.0.

5. Vale suportar Windows como servidor nesta versao?
   - Nao oficialmente. Windows pode permanecer como melhor esforco/laboratorio enquanto Docker Desktop, WSL2, licenciamento, firewall, reboot, backup, atualizacao e disponibilidade nao forem validados como operacao real.

6. Como o instalador deve detectar uma instalacao existente?
   - Por `.env`, `TECHDESK_PROJECT_NAME`, containers do Compose, volume nomeado do PostgreSQL, banco respondendo e estado de setup da aplicacao.

7. Como impedir perda de dados em rerun?
   - Rerun deve preservar `.env`, secrets, volume, banco e ADMIN; nunca executar `down -v`, remover volumes, trocar secrets silenciosamente, resetar admin ou sobrescrever configuracao sem modo explicito.

8. Como separar instalacao, upgrade e repair?
   - Usar comandos ou flags claros: `install` para nova instalacao, `upgrade` para backup + troca de imagens + migrations + health + smoke, e `repair` para diagnostico/correcao nao destrutiva.

9. O onboarding web precisa de mudanca no banco?
   - Sim, provavelmente. A recomendacao e um singleton `AppSettings` com `setupCompleted` e `setupCompletedAt`; alternativa seria colocar `setupCompleted` em `CompanySettings`, mas isso mistura estado tecnico com dados da empresa.

10. Como proteger o onboarding de acesso indevido?
    - Controlar por estado persistido; apos conclusao, redirecionar para dashboard; se ja existir ADMIN ativo, exigir login ADMIN para continuar; se nao existir ADMIN, permitir criar o primeiro apenas no setup inicial; nunca expor secrets.

11. O escopo total ainda e seguro para uma v1.1?
    - Sim, desde que os MUST sejam estorno auditavel e installer/setup experience; CPF/CNPJ e onboarding entram como SHOULD; painel seguro e code splitting so entram se nao colocarem a entrega em risco.

12. Installer e estorno devem ser os dois focos principais?
    - Sim. Estorno fecha uma lacuna operacional critica de estoque, e installer/setup reduz atrito para instalacao real da v1.1.

13. CPF/CNPJ ainda cabe sem inflar a versao?
    - Cabe como SHOULD, porque e opcional, melhora identificacao do cliente e nao deve afetar tracking publico. Deve ser implementado com minimizacao de dados e RBAC claro.

14. Code splitting deve ser obrigatorio ou opcional?
    - Opcional, como COULD. O bundle atual merece atencao, mas nao deve bloquear estorno, installer, upgrade ou piloto real.

15. Qual e a primeira implementacao depois da aprovacao deste plano?
    - Primeira implementacao geral: Etapa 1, modelagem/migration do estorno e campos-base aprovados. Primeira implementacao do installer: separar formalmente modos `install`, `upgrade` e `repair` no bootstrapper/script.
