# TechDesk Pro v1.2.0 - Stage 2

## Scope

Stage 2 completes the mixed budget backend without changing the Stage 1 schema
or migration. Budget versions are immutable and may contain PART and SERVICE
items together, or SERVICE items only.

## Request contract

Both budget creation endpoints accept at least one item:

```json
{
  "items": [
    {
      "type": "PART",
      "partId": "7cb52e44-e0e8-4a72-884e-cb29ba1efdc9",
      "quantity": 1,
      "unitPrice": 250
    },
    {
      "type": "SERVICE",
      "description": "Operating system installation",
      "quantity": 1,
      "unitPrice": 100
    }
  ]
}
```

- `PART`: requires a valid active Part and rejects client-provided
  `description`. The stored description is a snapshot of `Part.name`.
- `SERVICE`: requires a trimmed description from 1 to 200 characters and
  rejects a non-null `partId`.
- `quantity` is a positive integer and `unitPrice` is positive.
- A legacy item without `type` remains a PART item when `partId` is present.
  An item without both `type` and `partId` is invalid; SERVICE is never inferred.

## Snapshots and totals

`BudgetItem.description` is immutable budget history. PART copies the current
Part name and SERVICE copies the submitted description. `unitPrice` is the
financial snapshot and is not read again from `Part.currentPrice`.

Totals use `Prisma.Decimal` and sum `quantity * unitPrice` across PART and
SERVICE items. Changes to a Part name or price do not alter an existing budget.

## Versioning and concurrency

There is no in-place budget update. Standard creation calculates V1, V2, and
later versions from the latest persisted version. Maintenance revision also
creates a new version and atomically moves the service order to
`BUDGET_CHANGED_AWAITING_APPROVAL` with one history entry.

Creation uses a PostgreSQL `FOR UPDATE` lock on the target ServiceOrder. The
lock is granular per service order. Inside the same transaction, the repository
checks that both the status and latest version still match the baseline read by
the request. If another request changed either value, the operation returns:

```text
HTTP 409
Budget version conflict. Reload the service order and try again
```

The unique constraint on `(serviceOrderId, version)` remains the final database
barrier. An expected Prisma `P2002` from this path is also mapped to the same
stable 409 response; constraint names, SQL, and Prisma internals are not exposed.
Budget and BudgetItems are created atomically, and revision status/history are
part of that transaction.

Concurrent requests from the same V1 produce one V2 and one 409. Requests for
different service orders use different row locks and both pass.

## Approval, stock, and reversal

Mixed and SERVICE-only budgets are valid for approval. Approval and rejection
continue to target the latest budget ID and use the existing RBAC and status
rules. Neither action creates a stock movement.

Only PART items from the latest budget participate in stock consumption.
Duplicate PART lines remain allowed and their approved quantities are summed;
there is no silent deduplication. SERVICE quantities never increase an approved
stock quantity, never create EXIT or REVERSAL movements, and do not participate
in reversible quantity. Existing net consumption after reversal remains intact.

## Read, print, and privacy

Authenticated service order detail returns every budget version in ascending
order. Each item includes `type`, snapshot `description`, `partId`, `quantity`,
and `unitPrice`; SERVICE returns `partId: null` and `part: null`. The current
frontend and print views render the snapshot first and do not require a Part for
SERVICE items. Legacy PART responses remain supported by the frontend guard.

Public tracking does not select budgets, customer documents, or item
descriptions, so this stage adds no public data exposure.

## RBAC

- Create budget or revision: ADMIN, TECHNICIAN.
- Approve or reject: ADMIN, RECEPTION.
- No role was added or broadened.

## Verification

The Stage 2 PostgreSQL integration suite covers legacy and explicit PART,
SERVICE-only, mixed totals, snapshots, validation and rollback, version history,
same-OS concurrency, different-OS concurrency, mixed approval/rejection,
SERVICE-only approval, stock isolation, duplicate PART lines, reversal, RBAC,
read shape, and OpenAPI.

Full backend and frontend regression commands are recorded in the final Stage 2
report.

## Risks and next stages

- PART `partId` and SERVICE nullability are application invariants in v1.2.0;
  adding database CHECK constraints would require a separate additive migration.
- Full approval/rejection state-machine serialization remains planned for Stage
  5, as scoped by the roadmap.
- The Stage 3 frontend can add the complete SERVICE item authoring experience;
  this stage only guarantees response, list, and print compatibility.
