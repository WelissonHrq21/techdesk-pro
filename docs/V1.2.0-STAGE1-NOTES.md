# TechDesk Pro v1.2.0 - Stage 1 Notes

## Scope

Stage 1 establishes the database and contract foundation for real budget items
and reliable stock. It does not deliver the complete mixed-budget form,
low-stock dashboard behavior or stock-history pagination.

Initial source commit:
`4c46f77a19bfc711014326d0cc94f54432158c13`.

The v1.1.1 tag remained at
`66746b2d71b8a67dae25f9db66e6bf2d970b55fd` locally and remotely. The initial
working tree was clean, `main` matched `origin/main`, and remote CI for the
initial commit was green.

## Previous schema

- `BudgetItem` had only quantity, unit price and a mandatory Part relation.
- The displayed item name depended on the current `Part.name`.
- `Budget` had a non-unique index on `serviceOrderId`.
- `Part` had current stock but no per-part minimum.
- `StockMovement` had separate `partId` and `createdAt` indexes.

Every existing BudgetItem was therefore a part item. There was no valid legacy
representation of a service-only item.

## New schema

### Budget item enum

`BudgetItemType` contains exactly:

- `PART`
- `SERVICE`

`SERVICE` is the general concept for labor and other quoted services. No
parallel `LABOR` enum was introduced.

### PART semantics

- `partId` is required by the API/domain.
- The Part must exist and be active.
- The client cannot submit or override the snapshot description.
- `description` is copied from `Part.name` when the item is created.
- Renaming the Part later does not change the budget snapshot.
- Omitting `type` remains compatible and is interpreted as `PART`.
- Quantity remains an integer of at least 1 and unit price remains positive.

### SERVICE semantics

- `type` must be `SERVICE`.
- `partId` may be omitted or explicitly null.
- A Part UUID is rejected instead of silently discarded.
- A trimmed description of 1 to 200 characters is required.
- Quantity and unit price use the same positive rules as PART.
- The stored Part relation is null and stock consumption does not target the
  service item.

The database makes `partId` nullable to support SERVICE. The type-to-Part
invariant is enforced in the Zod contract and domain preparation service, as
planned. No unsupported Prisma check constraint was introduced.
The optional relation explicitly preserves the historical `ON DELETE RESTRICT`
policy, so deleting a referenced Part cannot erase the item-to-Part link.

## Snapshot policy

`BudgetItem.description` is an immutable commercial snapshot. Legacy and new
PART items use the Part name at budget creation time. SERVICE uses the submitted
service description. Updating a Part never updates historical BudgetItems.

## Stock foundation

`Part.minimumStock` is a non-null integer with default `0`.

Semantics:

- values below zero are rejected by create/update API validation;
- zero means no positive minimum quantity is configured;
- zero does not mean unlimited stock;
- the migration does not modify `Part.stock`;
- dashboard alerts and stock filtering remain for a later Stage.

The former `StockMovement(partId)` index was replaced with
`StockMovement(partId, createdAt)`. The leading `partId` remains usable for part
lookups and the second column supports chronological part history. The global
`createdAt` index remains because the dashboard queries recent movements across
all parts.

## Budget version uniqueness

`Budget(serviceOrderId, version)` is now unique. The migration first audits for
duplicates and aborts if any exist. It does not delete, renumber or repair
legacy budgets. The compound index replaces the redundant single-column
`serviceOrderId` index while retaining its lookup prefix.

The application still calculates the next version as before. Translating a
concurrent unique conflict into a stable HTTP 409 belongs to the later
concurrency Stage; database integrity is already protected here.

## Migration strategy

Migration:
`20260822000100_add_budget_item_types_and_stock_foundation`.

Order of operations:

1. Create `BudgetItemType`.
2. Add nullable `type` and `description` columns.
3. Join legacy BudgetItems to Part and backfill `type=PART` plus the Part name.
4. Abort if any legacy item could not be backfilled.
5. Make type/description mandatory, default type to PART and make `partId`
   nullable.
6. Add `Part.minimumStock` with default 0.
7. Abort if duplicate `(serviceOrderId, version)` data exists.
8. Replace the Budget index with the compound unique index.
9. Replace the stock movement part index with the part/date index.

No previous migration was edited or squashed.

## Contracts and compatibility

- Existing part-only requests without `type` still create PART items.
- Budget responses now include `type`, immutable `description`, and nullable
  `partId`/`part` for SERVICE.
- Part create/update contracts accept non-negative `minimumStock`; create
  defaults it to zero.
- OpenAPI documents PART/SERVICE input rules and minimum stock.
- No stock-history pagination endpoint was documented or implemented.
- Public tracking response was not changed.

The frontend has only compatibility work in this Stage:

- it displays snapshot descriptions in budget history and print;
- it tolerates nullable Part relations;
- service lines are excluded from consumption controls;
- existing service lines are preserved when the current part-only revision form
  submits a revision;
- the complete mixed-item creation/editing experience remains deferred.

## Tests and regressions

Added integration coverage verifies:

- legacy part-only payload defaults to PART;
- Part name snapshot remains unchanged after Part rename;
- mixed PART/SERVICE total and nullable relation;
- SERVICE does not create or receive stock consumption;
- mixed budget revision;
- PART without `partId` is rejected;
- SERVICE with empty description is rejected;
- SERVICE with a Part UUID is rejected;
- minimum-stock default/configuration/negative validation;
- same version on different OS is allowed;
- duplicate version on the same OS is blocked by Prisma/PostgreSQL;
- OpenAPI exposes the new contracts.

The complete existing integration suite also covers ENTRY, EXIT, partial/total
REVERSAL, net consumption, revised-budget consumption, excess-consumption
blocking, delivered/cancelled status protection, tracking privacy, RBAC and
onboarding.

## Remaining risks and next Stages

- Full mixed-budget UX remains for the planned frontend Stage.
- Dashboard and part-list low-stock calculations do not use `minimumStock` yet.
- Movement history is indexed but not paginated yet.
- Manual stock EXIT concurrency is unchanged.
- Budget/status concurrency needs locks or conditional writes and friendly 409
  responses.
- Raw SQL could violate the PART/SERVICE relation because this invariant is
  intentionally application-enforced; all supported writes must use the API.
- Authentication/session, QR and broader reporting work remain out of Stage 1.

No P0 or P1 issue was found during Stage 1.
