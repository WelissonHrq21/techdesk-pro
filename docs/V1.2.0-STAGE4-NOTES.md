# TechDesk Pro v1.2.0 - Stage 4

## Scope

Stage 4 makes stock balance updates reliable under concurrency and makes stock
history scalable. It activates the existing `Part.minimumStock` field, derives a
stock status in the API, adds server-side list and history filters, and updates
the parts frontend. The Prisma schema and all migrations remain unchanged.

## Stock status and minimum stock

`stockStatus` is derived by one backend helper and is returned with Part
responses. It is never persisted:

- `stock === 0` is always `OUT_OF_STOCK`.
- `minimumStock > 0` and `0 < stock <= minimumStock` is `LOW_STOCK`.
- Every remaining positive balance is `OK`.
- `minimumStock === 0` disables only the low-stock alert; it does not hide an
  out-of-stock Part.

The existing create and update validation requires an integer greater than or
equal to zero. Updating `minimumStock` does not update `stock`. The parts list
accepts `stockStatus=OK|LOW_STOCK|OUT_OF_STOCK`, combines it with search in the
database query, and keeps the legacy `maxStock` filter for compatibility.

## Atomic stock operations

Manual EXIT now locks the Part row with `SELECT ... FOR UPDATE`, reads the
latest active state and balance inside the transaction, decrements stock, and
creates the EXIT movement in the same transaction. Insufficient balance returns
HTTP 409 and leaves both the balance and movement history unchanged.

ENTRY uses the same Part lock and an atomic Prisma increment, preventing lost
updates. Service-order consumption keeps its ServiceOrder lock and then locks
the Part. A manual EXIT linked to an OS follows the same ServiceOrder-to-Part
order. REVERSAL preserves its movement audit lock, then locks ServiceOrder and
Part before incrementing. The shared Part lock serializes manual EXIT, OS
consumption, ENTRY, and REVERSAL only for the affected Part.

PostgreSQL integration tests repeat concurrent EXIT against a balance of one
five times. Each round produces one 201, one 409, a final balance of zero, and
one EXIT movement. Additional tests cover concurrent ENTRY `+2/+3`, manual EXIT
against OS consumption, and manual EXIT against REVERSAL.

## History contract

`GET /parts/:id/stock-movements` now returns the standard `{ data, meta }`
pagination envelope. Calling it without query parameters returns page 1 with 20
items. `limit` is capped at 100.

Supported filters are `type`, `dateFrom`, and `dateTo`. Dates use UTC calendar
days and both boundaries are inclusive. Results are ordered by `createdAt DESC,
id DESC`, providing stable pagination even when timestamps match. A 105-item
integration scenario proves six pages without duplicate or missing IDs.

The existing `StockMovement_partId_createdAt_idx` is used by PostgreSQL as a
backward index scan for the history query. The `id` tie-breaker adds an
incremental sort only within equal timestamps, so no additional index or
migration was justified.

The response shape change from an unlimited array to a paginated object is an
intentional internal API change. The bundled frontend was updated in the same
stage.

## Frontend UX

Part create and edit forms expose `Estoque minimo`, with `0 = sem alerta de
estoque minimo`. List and detail views show current stock, minimum stock, and a
text badge rather than relying only on color. Stock status filters are stored in
the URL and sent to the backend together with search.

Part history has Type, De, and Ate controls, a clear action, and the shared
Previous/Next pagination component. Filter changes return to page 1 and every
filter is part of the React Query key. Part detail, list, history, and dashboard
summary invalidations remain scoped after ENTRY, EXIT, consumption, and
REVERSAL.

An HTTP 409 from a stale manual EXIT keeps the dialog and authenticated page
open, shows a specific message, and refetches the Part and current history. All
movement form controls are disabled while submitting. Parts and movement
history use stacked records on narrow screens and tables on desktop.

- Backend integration: 95 passed, 1 skipped; includes PostgreSQL concurrency.
- Frontend component/integration: 80 passed across 17 files.
- Minimum-stock semantics, negative validation, combined search/status filter,
  pagination validation, type/date combinations, stable order, and OpenAPI are
  covered.
- Frontend coverage includes stock badges, minimum rendering/editing, mobile
  structure, server filters, pagination, type/date filters, ENTRY invalidation,
  stale EXIT 409/refetch/session preservation, and existing REVERSAL refresh.
- Existing suites continue to cover OS consumption, net consumed quantity,
  PART budget limits, SERVICE stock isolation, and DELIVERED reversal blocking.
- Backend typecheck/build/audit and frontend lint/build/audit are final release
  gates for this stage.

## Risks

- Page-number pagination is stable for a fixed dataset. New movements inserted
  while an operator moves between pages can shift later offsets, which is
  standard offset-pagination behavior and acceptable for this operational
  history.
- The history endpoint response changed shape. External clients, if introduced,
  must consume the pagination envelope.
- Low-stock dashboard expansion remains outside Stage 4 to keep this change
  focused; existing dashboard invalidation is preserved.
