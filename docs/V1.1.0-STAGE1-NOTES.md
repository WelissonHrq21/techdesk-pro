## Schema Change

`StockMovementType` now supports:

```prisma
enum StockMovementType {
  ENTRY
  EXIT
  ADJUSTMENT
  REVERSAL
}
```

`StockMovement` now has a nullable self-reference:

```prisma
reversalOfMovementId String?
reversalOfMovement   StockMovement?  @relation("StockMovementReversals", fields: [reversalOfMovementId], references: [id])
reversals            StockMovement[] @relation("StockMovementReversals")

@@index([reversalOfMovementId])
```

## Migration

Created migration:

```text
prisma/migrations/20260817020802_add_stock_movement_reversals/migration.sql
```

Relevant SQL:

```sql
ALTER TYPE "StockMovementType" ADD VALUE 'REVERSAL';

ALTER TABLE "StockMovement" ADD COLUMN "reversalOfMovementId" TEXT;

CREATE INDEX "StockMovement_reversalOfMovementId_idx"
ON "StockMovement"("reversalOfMovementId");

ALTER TABLE "StockMovement"
ADD CONSTRAINT "StockMovement_reversalOfMovementId_fkey"
FOREIGN KEY ("reversalOfMovementId")
REFERENCES "StockMovement"("id")
ON DELETE SET NULL
ON UPDATE CASCADE;
```

The migration preserves existing movements because `reversalOfMovementId` is nullable.

## PostgreSQL Enum

`REVERSAL` is added with:

```sql
ALTER TYPE "StockMovementType" ADD VALUE 'REVERSAL';
```

This is additive and works for clean install and upgrade. Rollback is not a simple reverse migration in PostgreSQL because removing enum values is not generally safe as a normal downgrade path. Operational rollback remains backup/restore based.

## Generated SQL Adjustment

Prisma initially generated an unrelated statement:

```sql
ALTER TABLE "ServiceOrder" ALTER COLUMN "publicToken" DROP DEFAULT;
```

This was removed from the Stage 1 migration because it is unrelated to auditable reversal and violates the task boundary.

Cause found: an existing schema/migration mismatch from the previous `publicToken` migration, where the database default is `gen_random_uuid()` while Prisma schema uses `@default(uuid())`.

Decision: do not change `ServiceOrder.publicToken` in this stage. Keep Stage 1 migration focused only on stock reversal.

## Database Guarantees

The database now guarantees:

- `REVERSAL` is a valid `StockMovementType`.
- `reversalOfMovementId` can reference an existing `StockMovement`.
- Invalid `reversalOfMovementId` values are rejected by FK.
- Existing `StockMovement` rows remain valid with `reversalOfMovementId = null`.
- Queries by `reversalOfMovementId` are indexed.

## Service Must Guarantee Later

Stage 2 must enforce business rules:

- `REVERSAL` points to an original `EXIT`.
- Original `EXIT` is never changed or deleted.
- Partial reversal is allowed.
- Total reversal is allowed.
- Multiple partial reversals are allowed.
- Sum of reversals never exceeds original `EXIT.quantity`.
- `partId` of reversal matches original movement.
- `serviceOrderId` of reversal matches original movement.
- User responsible is recorded.
- Reason is required.
- Stock increment and reversal creation happen in one transaction.
- Concurrency cannot create excess reversal.
- OS status must be `IN_MAINTENANCE` or `FINISHED`.
- `DELIVERED` is not allowed.
- RBAC: `ADMIN` and `TECHNICIAN` allowed, `RECEPTION` forbidden.
