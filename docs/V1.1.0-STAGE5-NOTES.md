# TechDesk Pro v1.1.0 - Stage 5 Notes

## Scope

Stage 5 evolves the v1.0.0 distribution package into a setup bootstrapper with explicit operations:

- `install`
- `status`
- `repair`
- `upgrade`

The setup layer manages infrastructure only: Docker, Compose, images, PostgreSQL, `.env`, secrets, ports, migrations through the existing API startup, health checks, logs, metadata, backup and upgrade flow.

It does not implement web onboarding, company setup, users wizard, GUI installer, Windows production support, JWT redesign or app functional configuration.

## Installation States

Supported conceptual states:

- `NOT_INSTALLED`
- `INSTALLED_HEALTHY`
- `INSTALLED_UNHEALTHY`
- `PARTIAL_INSTALLATION`

Detection considers:

- `.env`
- `techdesk-installation.json`
- Compose file
- Compose-labeled containers
- Compose-labeled volumes
- frontend `/health`
- API `/api/ready`

If database/container/volume signals exist without enough configuration, setup refuses destructive install and classifies the situation as partial or unhealthy.

## Metadata

File:

```text
deploy/techdesk-installation.json
```

Fields:

- `installationId`
- `version`
- `installedAt`
- `lastUpgradeAt`
- `projectName`
- `frontendPort`
- `installerVersion`

Secrets are intentionally excluded:

- no `POSTGRES_PASSWORD`
- no `JWT_SECRET`
- no `ADMIN_PASSWORD`
- no tokens

Writes use a temp file then `mv` to reduce partial write risk.

## Preflight

The bootstrapper checks before destructive or expensive work:

- OS and official platform warning.
- Architecture.
- CPU.
- RAM.
- Free disk space.
- Port format and availability for install.
- Docker CLI.
- Docker daemon.
- Docker Compose Plugin.
- UFW warning when active and port does not appear allowed.

Critical preflight failures stop install/repair/upgrade before pull/migrations.

## Secrets and Env

The setup generates:

- `POSTGRES_PASSWORD`
- `JWT_SECRET`

Generation uses `openssl rand` when available and `/dev/urandom` fallback.

The setup does not print secrets and does not write them to metadata.

`.env` is created only when absent. Existing `.env` is not overwritten silently.

Linux permissions:

- `.env`: best effort `chmod 600`
- metadata: best effort `chmod 600`
- logs/backups directories: best effort restrictive permissions

## Install

Flow:

1. Detect installation state.
2. Collect minimal configuration.
3. Run preflight.
4. Generate `.env` and secrets.
5. Validate Compose config.
6. Pull versioned images.
7. Start PostgreSQL.
8. Start API and migrations through existing production startup.
9. Start frontend.
10. Wait for `/health` and `/api/ready`.
11. Run idempotent admin seed.
12. Write metadata only after health/ready pass.

Second install is blocked when any installation signal exists.

## Status

`./techdesk status` reports:

- version
- installation state
- Docker state
- Compose availability
- containers when possible
- frontend health
- API ready
- local and LAN URLs

It does not show secrets.

Exit code:

- `0` when installed and healthy.
- non-zero otherwise.

## Repair

Repair is non-destructive.

It may:

- run Compose config.
- pull known configured images.
- run `compose up -d`.
- restart missing/stopped services.
- wait for health/ready.
- run admin seed idempotently.
- write metadata if the repaired installation becomes healthy.

It never:

- runs `down -v`.
- removes volumes.
- resets database.
- changes secrets.
- performs downgrade.
- restores backup automatically.

## Upgrade

`./techdesk upgrade --version X.Y.Z`:

1. Detects current version.
2. Blocks same-version upgrade.
3. Blocks downgrade using SemVer comparison.
4. Runs preflight.
5. Runs mandatory backup using existing `backup.sh`.
6. Requires backup script success, including non-empty dump, `pg_restore -l` and SHA256.
7. Pulls target versioned images.
8. Updates `.env` image/version values.
9. Runs `compose up -d`.
10. Waits for health/ready.
11. Updates metadata only after smoke succeeds.

Downgrade is not supported. Migration rollback is not attempted.

If health fails after target images are applied, backup and data are preserved, logs are kept, and no destructive rollback is attempted.

## Versioning

SemVer comparison is numeric, not string based:

- `1.10.0 > 1.9.0`
- `1.0.0 < 1.1.0`
- `v1.1.0 == 1.1.0`

The current `deploy/VERSION` remains `1.0.0` because v1.1.0 production images are not published in this stage.

The Stage 5 architecture supports v1.1.0 once release images exist, without pretending the final release is already available.
