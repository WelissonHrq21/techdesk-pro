# TechDesk Pro v1.1.0 - Stage 4 Notes

## Scope

Stage 4 adds optional CPF/CNPJ identification to `Customer`.

Included:

- Nullable `Customer.document`.
- Unique normalized document when present.
- CPF validation with verifier digits.
- Numeric CNPJ validation with verifier digits.
- Customer search by normalized or formatted document.
- Backend minimization by role.
- Frontend form, mask, validation, detail display, and search support.
- OpenAPI update.
- Upgrade migration validation.

Not included:

- Onboarding.
- Installer/setup experience.
- `AppSettings`.
- JWT changes.
- Code splitting.
- New print exposure.
- CNPJ alphanumeric support.

## Migration

Migration:

```text
prisma/migrations/20260817035000_add_customer_document/migration.sql
```

Changes:

```sql
ALTER TABLE "Customer" ADD COLUMN "document" TEXT;
CREATE UNIQUE INDEX "Customer_document_key" ON "Customer"("document");
```

The column is nullable. Existing customers keep `document = null`.

PostgreSQL unique indexes allow multiple `NULL` values, so existing and future customers without document can coexist.

## Normalization

Input is normalized by the backend before persistence.

Examples:

```text
529.982.247-25 -> 52998224725
11.222.333/0001-81 -> 11222333000181
```

Contract:

- Field absent on update: does not change the document.
- `document: null`: removes the document.
- `document: ""` or whitespace: removes the document.
- Filled document: stores digits only.

## Validation

Validation is centralized in:

```text
src/utils/customerDocument.ts
```

CPF:

- Must have 11 digits.
- Must pass verifier-digit calculation.
- Repeated digit sequences are rejected.

CNPJ:

- Must have 14 digits.
- Must pass traditional numeric CNPJ verifier-digit calculation.
- Repeated digit sequences are rejected.

## CNPJ Alphanumeric

The Receita Federal CNPJ alphanumeric format is already part of the 2026 transition for new registrations.

Stage 4 intentionally supports only traditional numeric CNPJ because this task explicitly required storage with digits only. Alphanumeric CNPJ support requires a different normalization/storage contract and must be handled in a future scoped task.

Reference used during implementation:

```text
https://www.gov.br/receitafederal/pt-br/acesso-a-informacao/acoes-e-programas/programas-e-atividades/cnpj-alfanumerico
```

## Uniqueness

Uniqueness applies to the normalized value.

Examples:

```text
529.982.247-25
52998224725
```

Both are treated as the same document. Duplicate create/update attempts return `409` with:

```text
Customer document already exists
```

Prisma `P2002` errors are translated to domain errors for both `document` and existing `email` uniqueness.

## Search

`GET /customers?search=...` now searches by:

- name;
- phone;
- email;
- normalized document when the search term contains digits.

Formatted input works because the search term is normalized before adding the document condition.

## RBAC And Privacy

`ADMIN`:

- Can create/edit document.
- Can view document.
- Can search by document.

`RECEPTION`:

- Can create/edit document.
- Can view document.
- Can search by document.

`TECHNICIAN`:

- Cannot create/edit customers by existing RBAC.
- Can search customers for technical flows, but `document` is omitted from response payloads.
- Can open service-order detail, but `serviceOrder.customer.document` is omitted.

Minimization is centralized through:

```text
src/serializers/customerSerializer.ts
```

## Public Tracking

`GET /public/service-orders/:token` still does not return `Customer`.

Regression test confirms the response does not contain the document value.

## Prints

Stage 4 does not add CPF/CNPJ to:

- OS receipt print.
- Budget print.

Decision: do not expand exposure of personal data in printed documents until there is an explicit operational requirement.

## Logs

Logger redaction now includes:

- `req.body.document`.
- `request.body.document`.
- generic `document`.

This prevents CPF/CNPJ from being emitted if request body serialization is enabled.

## Frontend

Customer form:

- Adds optional `CPF/CNPJ`.
- Applies visual CPF/CNPJ mask.
- Validates CPF/CNPJ before submit.
- Sends normalized digits or `null`.

Customer detail:

- Shows formatted document when the backend sends it.
- Does not show the document block when the property is omitted.

Customer search:

- Search input is sent to the backend; backend remains responsible for normalization.

New service order:

- Customer search supports CPF/CNPJ.
- Document is shown only when present in the authorized backend response.
