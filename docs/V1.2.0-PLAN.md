# TechDesk Pro v1.2.0 - Planning and Scope

## Executive summary

TechDesk Pro v1.1.0 is a production-capable operational system with a coherent
service-order workflow, role-based access, auditable stock consumption and
reversal, public tracking, printable documents, first-run onboarding, backup
and restore tooling, and a hardened image promotion pipeline.

The v1.2.0 release should remain a controlled product release. Its recommended
theme is **real budgets and reliable inventory**. The two mandatory outcomes
are:

1. budgets can represent services or labor without creating fake parts; and
2. inventory alerts, history and critical balance updates remain trustworthy as
   the installation grows.

Three smaller outcomes are recommended after the mandatory scope: protect
critical service-order decisions against concurrent requests, add a safe QR
code for the existing public tracking URL, and revoke existing sessions after a
password change or administrative password reset.

This plan deliberately excludes accounting, external notifications, a generic
enterprise audit log, authentication cookie redesign, destructive restore from
the web UI and another installer redesign.

## Workflow audit

The implemented path is:

`RECEIVED -> IN_ANALYSIS -> AWAITING_APPROVAL -> BUDGET_APPROVED -> IN_MAINTENANCE -> FINISHED -> AWAITING_PICKUP -> DELIVERED`

The flow also supports rejection back to analysis, a changed budget awaiting new
approval, and cancellation from pre-maintenance states. Delivered and cancelled
orders are terminal. Transition history stores previous/new status, actor,
observation and time.

The workflow meets the current operational lifecycle. The clear gap is not a
missing status; it is concurrency control. Approval and rejection, or two
status actions based on the same old state, can both pass their initial checks
and produce contradictory history. This is a data-integrity improvement, not a
reason to add more statuses.

## Dashboard and reporting audit

Dashboard values are computed in the backend. It already provides useful queues
and stock signals:

- open OS and counts by operational status;
- created today and delivered today;
- out-of-stock and low-stock counts;
- ten recent service orders; and
- ten recent stock movements.

The delivered-today value correctly comes from transition history. The main
misleading value is low stock because every part is compared with the same
temporary threshold of 5. Cards and recent OS rows are not links to their
corresponding operational queues. There are no trends or value totals.

There is no reports module. The data can support **operational reporting** such
as OS by period/status and net parts consumed. Approved budget totals describe
approved proposals, not collected revenue. The system has no payment, invoice,
cash-flow, service-cost or accounting model, so revenue/financial reporting is
not valid for v1.2.0.

Classification:

- correct low-stock indicators: `MUST`;
- action links from dashboard to filtered queues: `COULD`;
- operational report/export foundation: `COULD`, after pagination work;
- revenue, profit or accounting dashboard: `NOT RECOMMENDED NOW`.

## Search, pagination and performance audit

Current paginated searches:

- customers: name, phone, email and normalized/formatted document;
- equipment: type, brand, model, serial and customer name, plus customer filter;
- service orders: number, customer, phone, equipment fields, serial, one or
  more statuses, date interval, customer/equipment, sort and pagination;
- parts: name, brand, supplier and maximum stock.

Customer, equipment, service-order and part lists use offset pagination with a
maximum page size of 100 and lightweight list projections. This is appropriate
for 1,000 customers and 10,000 OS in the intended single-office deployment.
Case-insensitive `contains` searches will eventually need `pg_trgm` or full-text
search only after measured database growth warrants it.

Concrete risks:

1. `GET /parts/:id/stock-movements` returns the complete history with relations.
   At 50,000 total movements, a frequently used part can create a large query,
   payload and browser table.
2. The low-stock frontend requests `maxStock=5` and then removes zero-stock rows
   in memory. The server total still includes those removed rows, so pagination
   counts and pages can be wrong or appear partially empty.
3. A service-order detail loads every budget/item, status history and movement.
   This is acceptable now, but old/high-activity OS need a measured payload
   threshold before separate timeline pagination is introduced.
4. The manual EXIT flow reads balance outside its write transaction. Two
   simultaneous exits can both validate and drive stock below zero.

Relevant indexes already exist for customer document/email, equipment serial,
service-order number/public token/status/createdAt/customer/equipment and stock
movement part/SO/reversal/createdAt. Missing indexes or constraints tied to real
queries are:

- `StockMovement(partId, createdAt)` for paginated part history;
- optionally `ServiceOrderHistory(serviceOrderId, createdAt)` if timeline
  pagination is introduced; and
- a unique `Budget(serviceOrderId, version)` constraint for version integrity.

No speculative indexes should be added for `contains` search without query-plan
evidence.

## Security and privacy audit

Existing controls include bcrypt password hashes, Zod validation, role and
domain authorization, Helmet, a 1 MB JSON body limit, an explicit CORS allowlist,
generic 500 responses, log redaction, login rate limiting (20 per 15 minutes),
public-tracking rate limiting (60 per minute), private database networking and
production Swagger disablement.

Public tracking exposes only OS number/status/timestamps and equipment
type/brand/model. It omits customer data, document, password, diagnosis,
budgets, movements, history, users and internal user IDs. A QR code containing
only that URL/token does not expand the existing data contract. It must never
contain CPF/CNPJ, password, diagnosis, JWT or internal IDs.

Security findings:

| Severity | Finding | Roadmap decision |
| --- | --- | --- |
| P0 | None found. | No emergency work. |
| P1 | None found. | No release blocker. |
| P2 | Manual stock exit can overdraw under concurrent requests. | Included in inventory reliability `MUST`. |
| P2 | Concurrent budget version creation and approval/rejection/status decisions lack database/transaction serialization. | Budget uniqueness is part of the budget `MUST`; decision serialization is `SHOULD`. |
| P2 | Password change/reset does not revoke already issued JWTs until their configured expiry (default 8h). | `SHOULD`, using a small token-version design. |
| P3 | JWT in `localStorage` increases impact if an XSS vulnerability is introduced. | Accepted for v1.2.0; HttpOnly-cookie redesign remains `NOT NOW`. |
| P3 | Broad administrative changes do not have a dedicated security audit log. | Keep `NOT NOW` until a concrete accountability requirement exists. |

Role changes and deactivation already take effect immediately because the auth
middleware reloads the user. A token-version field would address password
changes without introducing refresh tokens, cookie/CSRF complexity or a session
table. Full JWT redesign remains disproportionate to current risk.

## Technical debts that matter

1. A budget item can only be a part. This forces fake inventory records for
   labor or services and couples a commercial proposal to stock consumption.
2. Low stock is hardcoded at 5 in backend and frontend (`ADR-016`).
3. Per-part movement history is unbounded and the low-stock filter corrupts its
   own pagination semantics.
4. Manual stock exit is not concurrency-safe.
5. Budget version has no composite unique constraint, and state decisions do not
   use a lock or conditional update.
6. OpenAPI covers paths but not all contracts in depth.
7. Critical tests are strong for the main happy path and reversal, but missing
   for dashboard calculations, stock-history pagination, manual-exit concurrency,
   concurrent budget decisions, print content and session revocation.

Repository marker audit found no actionable source `TODO`, `FIXME`, `HACK`,
`XXX`, deprecated package marker or workaround comment. The meaningful planned
debts are recorded in architecture decisions, especially low stock, token
storage/revocation and future audit logging.

## Recommended scope

### V1.2.0 MUST

1. **Budget lines for parts and services.** This closes the largest real-use gap
   without introducing accounting. Existing proposal versions remain immutable
   snapshots, and only part lines participate in stock consumption.
2. **Reliable and scalable inventory.** Add per-part minimum stock, correct
   server-side stock-state filtering, bounded movement history, matching indexes
   and atomic manual exits.

### V1.2.0 SHOULD

1. Serialize critical OS approval/rejection/status decisions and return a
   friendly 409 for stale actions.
2. Add QR tracking to the OS detail and printed protocol using only the existing
   safe public URL/token.
3. Revoke old JWTs after self-service and administrative password changes using
   token versioning, without redesigning auth around cookies or refresh tokens.

### V1.2.0 COULD

- Link dashboard counts and recent rows to existing filtered queues.
- Add an optional part SKU/code if a pilot catalog demonstrates the need.
- Improve changed OpenAPI operations from summary-only to complete schemas.
- Add budget validity/notes or protocol terms after exact business wording and
  versioning semantics are decided.
- Prototype bounded operational exports only after stock-history pagination and
  query measurements.
- Show a safe read-only system panel in a later product/operations iteration.

### NOT NOW

- payment, invoice, revenue, profit, cash-flow or accounting reports;
- discounts/taxes with no agreed commercial model;
- generic AuditLog without a concrete compliance/accountability requirement;
- refresh-token/session-table or HttpOnly-cookie authentication redesign;
- WhatsApp, email or SMS integrations;
- logo upload or arbitrary file storage;
- customer/equipment forms expanded with many niche fields;
- destructive database restore from the browser;
- full UI redesign or dedicated native mobile app;
- `pg_trgm`/full-text search without measured need;
- broad service-order timeline pagination before payload thresholds show need;
- installer rewrite, database migration orchestration for multiple API replicas;
- SBOM, Cosign, action SHA pinning and installer image digest pinning in this
  product release. They remain valid supply-chain backlog items.

## Data model impact

Proposed additive model changes:

1. `BudgetItemType` with `PART` and `SERVICE`.
2. `BudgetItem.type`, default/backfilled as `PART`.
3. `BudgetItem.description` as an immutable snapshot.
4. `BudgetItem.partId` nullable only for `SERVICE`; API/domain validation enforces
   the type-specific invariant.
5. Unique `Budget(serviceOrderId, version)`.
6. `Part.minimumStock Int` with migration default 0 and input minimum 0.
7. Composite `StockMovement(partId, createdAt)` index.
8. `User.tokenVersion Int @default(0)` only if the session-revocation SHOULD is
   accepted.

Do not persist `LOW_STOCK`: it is derived from active part balance and its
minimum. Preserve out-of-stock as a separate operational category. A minimum of
0 means no positive minimum has been configured; it does not mean unlimited
stock.

The migration must backfill budget descriptions from the related part before
making description mandatory. No existing budget, price snapshot, stock balance,
movement, reversal or history may be rewritten semantically.

## API impact

Recommended contracts:

- budget create/revision accepts a discriminated item union:
  - PART: `type`, `partId`, optional client description override policy,
    `quantity`, `unitPrice`;
  - SERVICE: `type`, `description`, `quantity`, `unitPrice`;
- budget responses include `type`, `description`, nullable `partId`/`part` and
  retain string-safe decimal values;
- part create/update includes `minimumStock`;
- part list replaces ambiguous client-side `maxStock` behavior with an explicit
  server-side stock-state filter such as `ALL`, `OUT_OF_STOCK`, `LOW_STOCK`;
- `GET /parts/:id/stock-movements` accepts `page`, `limit`, optional `type`,
  `dateFrom`, `dateTo`, and returns `{ data, meta }`;
- stale decision/write conflicts use HTTP 409 and a stable friendly contract;
- JWT payload and auth middleware use an internal token version if included;
- public-tracking response stays unchanged.

Backward compatibility should be explicit. The frontend and backend images are
released together, but existing automation may use current budget payloads. The
API can temporarily treat an item with `partId` and no `type` as PART during the
v1.2 transition, document the compatibility behavior, and remove it only in a
future major contract change.

## Frontend impact

- Budget builder supports explicit Part/Service item modes without nested or
  oversized forms.
- Budget versions and prints show the immutable description and item kind.
- Consumption/reversal UI lists only PART items and preserves current net
  consumption behavior.
- Part forms show minimum stock; list/detail badges use the server semantics.
- Stock history uses pagination and filters; displayed counts refer to the
  returned/filtered history rather than all records loaded in memory.
- Stale 409 actions refetch and explain that another operator changed the OS.
- QR appears with a textual tracking URL/fallback in the protocol and OS detail.
- Password-change success explains that the user will sign in again if token
  revocation is included.

Current responsive grids and horizontally scrollable tables are functional for
mobile use, but dense tables require horizontal movement. v1.2.0 should verify
the budget builder, stock history, QR protocol and technician OS workbench at
mobile and desktop widths; it should not redesign every list.

## RBAC and privacy

- ADMIN: manage parts/minimums, manual entries/exits, users/settings and all
  existing operational actions.
- TECHNICIAN: create/revise mixed budgets, consume/reverse only PART lines and
  read stock/history as today.
- RECEPTION: approve/reject mixed budgets and read operational stock as today.
- Public: unchanged limited tracking payload only.

Minimum stock, service-line descriptions and proposal prices are internal. QR
codes encode only the public tracking URL. Do not include customer PII, equipment
password, diagnosis, JWT, user ID or internal database ID in QR content. The
TECHNICIAN customer-document minimization remains unchanged.

## Migration and upgrade strategy

1. Build migrations as additive and backward compatible.
2. Before migration, create and validate a v1.1.0 backup with SHA-256 and
   `pg_restore -l`/restore-check.
3. Add nullable/defaulted columns and indexes first.
4. Backfill every existing budget item as PART with a description snapshot.
5. Verify counts, totals, item-part relations, stock balances, reversal links and
   setup state before applying mandatory constraints.
6. Deploy the coordinated v1.2.0 API/frontend candidate and run `migrate deploy`
   through the approved container startup path.
7. Validate a populated v1.1.0 -> v1.2.0 upgrade and a clean v1.2.0 install.
8. Generate a post-upgrade backup and run restore-check.

Rollback is application-first only while the migrated schema remains backward
compatible. Do not automatically roll back the database. If validation fails
after a data-transforming migration, stop writes and restore the validated
pre-upgrade backup into an isolated database before any production replacement.
Document whether old v1.1.0 code tolerates the additive columns; never assume a
container rollback proves database rollback.

If token versioning is accepted, planned logout of all pre-upgrade sessions is
an explicit release note and smoke-test expectation.

## Testing strategy

### Backend integration

- mixed PART/SERVICE budget creation, totals and decimal serialization;
- service line without part, invalid type combinations and inactive/missing part;
- revisions preserve immutable versions and consumed-part constraints;
- service items never appear as consumable stock;
- concurrent budget creation preserves unique versions;
- per-part minimum boundaries, zero-stock separation and inactive parts;
- stock-state filters return correct rows and pagination metadata;
- movement history paging, type/date filters, ordering and maximum limit;
- simultaneous manual exits never create negative stock;
- approve/reject and duplicate transition races produce one winner and one 409,
  with one consistent history path;
- old JWT rejection/new JWT success after both password-change paths;
- public tracking remains minimal and rate-limited;
- dashboard low-stock count uses each part minimum.

### Frontend component/integration

- accessible mixed budget builder and conditional validation;
- totals, version history and printed service lines;
- consumption options exclude service items;
- stock filters and pagination preserve URL/query state;
- empty/error/loading states for each new query;
- friendly 409 refetch behavior;
- QR encodes the expected public URL and exposes a text fallback;
- password change clears session only after server success;
- all new controls/actions respect ADMIN/RECEPTION/TECHNICIAN roles.

### Regression and non-functional

- complete authenticated OS lifecycle with part consumption and reversal;
- current CPF/CNPJ normalization/privacy and onboarding;
- print protocol and budget at A4 width;
- mobile widths for reception, technician, inventory and public tracking;
- query/payload checks with 1,000 customers, 10,000 OS and 50,000 movements,
  concentrating movements on a small number of parts;
- dependency audit, typecheck, lint, build, Docker health/readiness and log-secret
  checks;
- OpenAPI path and schema assertions for changed contracts;
- installer install/status/repair/upgrade tests remain green.

Coverage percentage is secondary to these business invariants and concurrency
scenarios.

## Recommended stages

### Stage 1 - Data contracts and compatibility migration

- Objective: establish additive budget, stock and optional token-version fields.
- Dependencies: approved item discriminator/default semantics and low-stock rule.
- Backend: Prisma model, migration/backfill and serializers only.
- Frontend: types/contracts only; no feature exposure yet.
- Migration: PART backfill/description snapshot, budget unique key, minimum stock,

- Dependencies: Stage 1.

### Stage 5 - Critical decision concurrency

- Objective: prevent contradictory budget decisions/status histories.
- Dependencies: Stage 2.

- Migration: none.
- Tests: parallel approve/reject and status transitions.

### Stage 6 - Tracking QR and session revocation

- Objective: deliver two bounded usability/security improvements.
- Dependencies: Stage 1 token version if approved; current public tracking.

- Frontend: QR on detail/protocol and post-password-change sign-in UX.
- Migration: token version only if not included in Stage 1.
- Tests: QR privacy/URL, rate-limit regression and old-token invalidation.

### Stage 7 - Release candidate and operational proof

- Objective: close documentation, regression, upgrade and release evidence.
- Dependencies: accepted MUST/SHOULD stages.
- Backend: complete changed OpenAPI schemas and release metadata.

## Release gates

1. Working tree traceable to an integrated `main` commit; CI fully green.
2. Backend/frontend unit and integration suites pass in isolation and CI.
3. Typecheck, lint, production builds and Prisma migration validation pass.
4. Database invariants pass on a production-shaped v1.1.0 copy.
5. Concurrency tests prove no negative stock, duplicate budget version or
   contradictory decision history.
6. OpenAPI documents and validates every changed endpoint/schema.
7. Docker candidate images build once with source/revision/version labels.
8. Clean install reaches health/ready and completes first-run onboarding.
9. Real populated v1.1.0 -> v1.2.0 upgrade preserves counts, totals, documents,
   balances, histories and reversals.
10. Pre-upgrade backup and post-upgrade backup pass SHA/listing/restore-check.
11. Repair, status, reboot persistence and non-root status behavior pass.
12. Security smoke confirms RBAC, PII minimization, redacted logs, rate limits,
    QR privacy and token revocation if included.
13. A4 printing and mobile reception/technician/stock flows pass visual smoke.
14. RC installer and images are tested by digest; exact digests are approved.
15. Final tags are promoted from approved digests with overwrite protection.
16. Final installation/upgrade smoke passes before GitHub Release publication.

The current hardened build/promotion pipeline should be reused, not redesigned.
Installer image-digest pinning, SBOM, Cosign and action SHA pinning remain later
supply-chain gates unless a separate security decision promotes them.

## Dependencies

`npm audit` reported zero known vulnerabilities in both projects at planning
time. No lockfile dependency has a deprecated marker. Routine patch/minor
updates are available. Prisma 7 and TypeScript 7 are major upgrades and must not
be combined with the product/data-contract changes in v1.2.0 without a separate
compatibility task. Dependency updates should be narrow, tested and motivated by
security or a required feature.

## Risks and controls

| Risk | Control |
| --- | --- |
| Service-line migration changes the central budget contract | Additive columns, populated-database backfill test, temporary part-item compatibility and full lifecycle regression. |
| Nullable `partId` weakens data integrity | Explicit item type, strict domain validation and migration verification; consider a SQL CHECK only if Prisma migration ownership remains clear. |
| Incorrect low-stock interpretation creates noisy purchasing alerts | Use the approved default 0 semantics and continue showing out-of-stock separately. |
| Offset pagination becomes slow at very deep pages | Accept at intended scale; measure before moving to cursor pagination. |
| Row locks create inconsistent ordering/deadlocks | Use one documented lock order and concurrency tests, following the proven consume/reversal pattern. |
| Token version logs all users out during upgrade | Make behavior explicit, coordinate frontend/backend, and include release notes/smoke. |
| QR token is shared beyond intended recipient | Keep response minimal, retain rate limit, allow link/token rotation only in a later task if misuse is observed. |
| Reports expand into false accounting | Keep them outside committed scope and label approved proposal values precisely. |
| Scope grows through logo, notifications, fields and installer work | Enforce MUST/SHOULD gates and move COULD items without blocking v1.2.0. |

## Open decisions

1. **Service item naming:** use generic `SERVICE`/“Serviço” (recommended) or a
   narrower `LABOR`/“Mão de obra”. Generic service lines fit more real proposals.
2. **Part description snapshot:** always copy the part name and disallow editing
   (recommended for traceability), or allow a proposal-specific description.
3. **Minimum-stock zero semantics:** `minimumStock=0` means no positive minimum
   is configured and disables the low-stock warning, while out-of-stock remains
   a separate alert.
4. **Stock history filters:** ship type plus date interval (recommended), or page
   only in the first increment.
5. **Concurrency implementation:** PostgreSQL row lock in one transaction
   (recommended for consistency with stock) or conditional update with affected
   row count.
6. **Session revocation:** include token version in v1.2.0 SHOULD (recommended)
   and accept planned re-login, or defer while retaining the 8-hour maximum.
7. **QR placement:** protocol and OS detail first (recommended); add budget only
   if customer testing shows value.
8. **COULD budget:** dashboard links may use remaining capacity; reports, system
   panel and SKU should not enter without explicitly removing another item.

## Final recommendation

**APPROVE V1.2.0 PLAN** with two mandatory capabilities, three bounded SHOULD
items and strict exclusion of accounting, external integrations and another
infrastructure-dominated sprint.
