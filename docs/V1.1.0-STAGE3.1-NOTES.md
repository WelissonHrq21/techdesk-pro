# TechDesk Pro v1.1.0 - Stage 3.1 Notes

## Scope

Stage 3.1 corrects the backend rule for service-order part consumption after auditable stock reversal.

Included:

- Net consumed quantity is now used when enforcing approved budget quantity.
- Budget revision protection now uses net consumed quantity.
- Consumption and reversal operations are serialized by service order to protect the budget invariant.
- Backend tests cover partial reversal, total reversal, multiple reversals, unrelated reversals, no-reversal regression, budget revision, and concurrent reverse/consume.

Not included:

- Schema changes.
- Frontend contract changes.
- `Customer.document`.
- `AppSettings`.
- Installer/setup changes.

## Cause

Stage 3 exposed a functional gap: reversing stock returned the physical stock, but the consume endpoint still calculated already consumed quantity using only gross `EXIT` movements.

That meant an OS could consume a part, reverse it, and still be blocked from consuming the restored approved capacity.

## Previous Formula

The previous consumption rule was equivalent to:

```text
consumed = SUM(EXIT.quantity)
```

The calculation lived in:

- `ConsumePartService`.
- `StockMovementRepository.sumExitedQuantityByPartAndServiceOrder`.
- `StockMovementRepository.findConsumedPartsByServiceOrder`.

`REVERSAL` movements were ignored by the operational consumption calculation.

## New Formula

The operational rule now uses:

```text
grossConsumed = SUM(EXIT.quantity)
reversed = SUM(REVERSAL.quantity linked to those EXIT movements)
netConsumed = grossConsumed - reversed
```

New consumption is allowed only when:

```text
netConsumed + requestedQuantity <= approvedQuantity
```

`REVERSAL` is linked through `reversalOfMovementId`; the calculation does not trust `partId` alone to reduce consumption.

## Gross vs Net Uses

Gross history preserved:

- Stock movement audit trail.
- Service-order movement history.
- Part movement history.
- Original `EXIT` quantity.
- Separate `REVERSAL` event records.

Net calculation used:

- Approved budget consumption limit.
- Already consumed quantity in budget revision protection.
- Effective service-order part consumption.

## Budget Versioning

The selected budget rule was not changed.

`ConsumePartService` continues using the same repository method as before:

```text
BudgetRepository.findLatestWithItemsByServiceOrderId(serviceOrderId)
```

Stage 3.1 only changed the consumed quantity compared against that budget item from gross to net.

## Concurrency

Consumption now runs inside a transaction that:

1. Locks the service order row with `FOR UPDATE`.
2. Calculates net consumed quantity.
3. Validates the approved budget limit.
4. Locks the part row with `FOR UPDATE`.
5. Validates stock.
6. Decrements stock and creates the `EXIT`.

Reversal now also locks the service order row before calculating reversible balance and creating `REVERSAL`.

This serializes relevant operations by service order and protects:

- two concurrent consumes for the same OS;
- reverse and consume for the same OS;
- budget invariant `netConsumed <= approvedQuantity`;
- stock consistency for service-order consumption.

The original movement row lock remains in place for reversal, preserving protection against double reversal of the same `EXIT`.

## Integrity

If inconsistent historical data ever makes:

```text
netConsumed < 0
```

the repository throws `Net consumed quantity is inconsistent` instead of silently masking the issue.

Normal application rules already prevent excessive reversal.

## Tests

Backend tests added or extended:

- `consume 2 -> reverse 1 -> consume 1` succeeds.
- additional consumption after restored capacity is exhausted fails.
- `consume 3 -> reverse 1 -> reverse 1 -> consume 2` succeeds.
- total reversal returns net consumed quantity to zero.
- consuming approved quantity again after total reversal succeeds.
- no-reversal behavior remains unchanged.
- reversal from another service order does not reduce this OS consumption.
- budget revision uses net consumed quantity.
- concurrent reverse/consume keeps net consumption within budget and stock consistent.

## Risks

- Manual stock exits remain historical/manual stock events and were not changed.
- Browser smoke was not necessary because no frontend contract changed.

## Result

Stage 3.1 resolves the Stage 3 risk: stock reversal now restores both physical stock and operational capacity inside the approved budget.
