# TechDesk Pro v1.1.0 - Final P2 Fix Notes

Validation date: 2026-08-22.

## Finding

The final Linux RC smoke completed without P0 or P1 findings. One P2 remained:
`/opt/techdesk-pro/techdesk status` initialized a persistent setup log before
running its read-only checks. In a root-owned runtime, an ordinary user could
not create that log and `status` stopped with `Permission denied`.

## Root Cause

`status_cmd` called `setup_log_init` unconditionally. The logger creates a file
under `/opt/techdesk-pro/logs`, which correctly uses private permissions and is
not writable by ordinary users. Logging behavior was not differentiated between
read-only and mutating commands.

The status path also relied on `.env` for project name and frontend port. That
file contains `POSTGRES_PASSWORD`, `JWT_SECRET` and other protected values, so
making it readable was not an acceptable fix.

## Correction

- `status` no longer creates a persistent setup log.
- Version, Compose project and frontend port fall back to public installation
  metadata, so `status` does not need to read `.env`.
- Container status uses Docker labels directly and does not load the Compose
  `.env` file.
- Docker socket denial is reported separately from daemon absence and logging
  failures.
- Health and ready checks remain available over HTTP even without Docker access.
- Mutating commands validate runtime access before initializing logs or changing
  files and return a clear administrative privilege diagnostic.
- Runtime bootstrap elevation happens before copying files to `/opt`; it no
  longer changes runtime ownership to the invoking ordinary user.

## Final Privilege Policy

- `STATUS`: read-only, no persistent log, supported without `sudo`.
- `INSTALL`: requests `sudo` before writing a protected `/opt` runtime.
- `REPAIR`: requires `sudo` when the runtime is root-owned.
- `UPGRADE`: requires `sudo` when the runtime is root-owned.
- `BACKUP`: requires `sudo` when protected logs/backups or `.env` require it.
- `RESTORE-CHECK`: follows the same protected runtime policy as backup.

Custom persistent runtimes that are intentionally writable by the operator can
run mutating commands without unnecessary elevation.

## Permission Policy

- `.env`: `600`.
- setup log files: `600`.
- logs directory: `700`.
- backups directory: `700`.
- `techdesk-installation.json`: `644`.

The metadata contains installation ID, version, timestamps, project name,
frontend port and installer version only. It contains no password, JWT secret,
database URL, token or functional customer data.

## Linux Harness

The setup suite ran through a real WSL2 Linux shell as uid/gid `1000`, without
root. Controlled harness scenarios proved:

- healthy `status` succeeds when the configured log path cannot be created;
- protected `.env` is not required for status;
- readable metadata supplies version, project and port;
- Docker socket denial produces a specific warning and does not become a log
  error;
- with Docker access available, container state is displayed without reading
  `.env`;
- install, repair and upgrade stop before logging when administrative access is
  required;
- writable privileged logging still creates a private `600` file.

Docker Desktop was not integrated into this WSL distribution, so socket-allowed
and socket-denied behavior was exercised with deterministic Docker CLI harnesses.
The shell, filesystem permissions and non-root process were real Linux behavior.
