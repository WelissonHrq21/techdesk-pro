# TechDesk Pro v1.1.0 - Stage 2 Notes

## Scope

Stage 2 implements the backend for auditable reversal of service-order stock consumption.

Included:

- `POST /stock-movements/:id/reverse`.
- Request validation with Zod.
- RBAC for `ADMIN` and `TECHNICIAN`.
- Transactional stock increment and `REVERSAL` creation.
- Concurrency protection for reversing the same original `EXIT`.
- OpenAPI update.
- Backend integration tests.

Not included:

- Frontend reversal UI.
- `Customer.document`.
- `AppSettings`.
- Installer/setup changes.

## Endpoint

```http
POST /stock-movements/:id/reverse
```

`id` is the original `StockMovement` id.

Request:

```json
{
  "quantity": 1,
  "reason": "Part will not be used"
}
```

Response shape follows the existing stock movement style:

```json
{
  "part": {},
  "movement": {},
  "originalMovement": {},
  "reversedQuantity": 1,
  "reversibleQuantity": 1
}
```

The `movement` object is the new `REVERSAL`.

## Rules

Allowed original movement:

- `EXIT` only.
- Must belong to a `ServiceOrder`.

Rejected original movement:

- `ENTRY`.
- `ADJUSTMENT`.
- `REVERSAL`.
- Manual `EXIT` without `serviceOrderId`.

Allowed service order statuses:

- `IN_MAINTENANCE`.
- `FINISHED`.

Blocked service order statuses:

- `RECEIVED`.
- `IN_ANALYSIS`.
- `AWAITING_APPROVAL`.
- `BUDGET_APPROVED`.
- `AWAITING_PICKUP`.
- `DELIVERED`.
- `CANCELLED`.
- Any other non-approved status.

The reversal does not change the service order status.

## RBAC

- `ADMIN`: allowed.
- `TECHNICIAN`: allowed.
- `RECEPTION`: forbidden with 403.

The endpoint is protected by the existing authentication middleware through the `/stock-movements` private route prefix.

## Reversible Balance

For the original `EXIT`:

```text
reversibleQuantity = EXIT.quantity - SUM(REVERSAL.quantity linked to EXIT)
```

If requested quantity exceeds the reversible balance, the endpoint returns 409.

## Transaction

The operation runs inside a Prisma interactive transaction:

1. Lock original movement with parameterized `SELECT ... FOR UPDATE`.
2. Load and validate the original movement.
3. Calculate already reversed quantity.
4. Validate available reversible balance.
5. Increment part stock.
6. Create `StockMovement` with `type = REVERSAL`.

This guarantees stock and movement are committed together or rolled back together.

## Concurrency Strategy

The implementation locks the original `StockMovement` row:

```sql
SELECT "id"
FROM "StockMovement"
WHERE "id" = $1
FOR UPDATE
```

Why this prevents double reversal:

- Concurrent reversals for the same original `EXIT` contend on the same locked row.
- The second transaction waits for the first to finish.
- After the lock is acquired, the second transaction calculates the reversible balance again.
- If the first transaction consumed the full balance, the second returns 409.

No raw user input is interpolated directly into SQL; Prisma parameterizes the query.

## ServiceOrderHistory Decision

No `ServiceOrderHistory` entry is created in Stage 2.

Reason:

- Current `ServiceOrderHistory` represents status transitions with `previousStatus` and `newStatus`.
- Reversal is an event without status change.
- Forcing it into that model would distort the history semantics.

The audit source for Stage 2 is `StockMovement.REVERSAL` linked to the original `EXIT`.

## Test Infrastructure Note

Adding a second integration test file exposed that the suite uses a shared PostgreSQL database and `resetDatabase`.

Decision:

- Set `fileParallelism: false` in Vitest config so integration files do not reset the same database concurrently.

This is test infrastructure only and does not affect production runtime.

## Security and Logs

No additional payload logging was added.

Existing logger redacts:

- `Authorization`.
- Password fields.
- Token fields.

The reversal reason is stored as audit data in `StockMovement.reason`.

## Risks

- Business-level reversal rules live in the service/repository transaction, not database constraints.
- `ServiceOrderHistory` does not represent non-transition events; a future generic event/audit model may be useful.
- Existing manual `EXIT` movements remain possible through the admin stock exit endpoint, but the reversal endpoint rejects them when they do not belong to an OS.
