# TechDesk Pro v1.2.0 - Stage 5 Notes

## Scope

Stage 5 hardens concurrent actions on service orders and revokes existing
sessions after security-sensitive user changes. It preserves the existing
workflow, RBAC rules, public tracking contract, installer and release pipeline.

## Service order serialization

Critical mutations use a PostgreSQL `SELECT ... FOR UPDATE` lock scoped to the
target `ServiceOrder`. The transaction then reloads and validates the current
status and relevant budget before applying state, history or stock effects.
There is no global lock, so actions on different service orders remain
independent.

The protected paths are:

- budget approval and rejection;
- service order status transitions, including cancellation;
- diagnosis updates that depend on the current status;
- budget revision creation and consumed-Part validation;
- Part consumption during maintenance;
- service-order stock reversals.

The existing transition matrix remains the source of truth. Normal and
concurrent requests use the same service-level transition and RBAC checks,
followed by transaction-level revalidation.

## Lock ordering

The shared order is:

1. `ServiceOrder`;
2. `StockMovement`, when a reversal is involved;
3. `Part`.

Budget revisions serialize on the service order before reading consumed stock.
Part consumption also locks the service order before the Part. Stock operations
that do not belong to a service order continue to lock only the affected Part.
This keeps different service orders concurrent and avoids the previous reversal
path acquiring locks in the opposite order.

Requests containing the same Parts in different payload orders do not create a
deadlock: revision creation is serialized by service order, while current stock
mutations affect one Part per request.

## Conflict semantics

Concurrent state conflicts return HTTP `409` with stable application messages.
Database, Prisma and SQL details are not exposed.

- Only one approve/reject decision can win for a budget.
- Duplicate approve, duplicate reject and stale two-tab decisions return `409`.
- Approval competing with a revision validates both status and latest budget;
  the stale operation returns `409`.
- Duplicate or incompatible status transitions create only one history record.
- Diagnosis does not overwrite data after a concurrent status transition.
- Part consumption revalidates status and latest budget before stock effects.
- Revision validation reads net consumed quantities while holding the OS lock.
- Reversal keeps its existing idempotency/conflict checks and stock guarantees.

No concurrent scenario duplicated stock effects or produced negative stock.

## Frontend behavior

The service-order workspace maps concurrency messages to friendly Portuguese
text, shows an error toast, refetches the complete service order (including
budgets and movements), closes stale dialogs and preserves authentication.
Failed Part consumption also invalidates Part, stock history, dashboard and OS
queries, preventing stale optimistic state.

Two-tab approval/rejection tests confirm that the second tab receives `409`,
refreshes to the winning state and keeps the session active.

## Session revocation

`User.tokenVersion` is an additive integer with default `0`. New JWTs carry the
current version. The authentication middleware reuses its existing User lookup
to compare the claim with the database value, so no additional request query was
introduced.

Tokens with a missing, non-integer or stale version receive HTTP `401` with the
stable `Session revoked` message. Tokens issued before this migration therefore
require a one-time login after upgrade.

The version is incremented atomically when:

- a user changes their own password;
- an administrator resets a password;
- an administrator changes a role;
- a user is deactivated.

Name and login edits do not revoke sessions. Reactivation cannot revive a token
issued before deactivation because the increment is retained. Concurrent admin
password resets use atomic increments and do not lose updates. Revocation is
isolated to the affected user.

After an own password change, the frontend clears the current session and sends
the user to login with `Senha alterada. Entre novamente.` A backend `401` caused
by revocation also clears the session and displays a reauthentication message.

`tokenVersion` is not returned in public User payloads or documented as a client
field. Passwords, hashes, tokens and JWT secrets remain covered by existing
serialization and logger redaction. Public service-order tracking remains
independent of authentication and token versions.

## Residual risks

- Correct concurrency behavior depends on PostgreSQL row-lock semantics; the
  integration suite therefore runs these scenarios against PostgreSQL rather
  than an in-memory substitute.
- Conflicting requests wait for the winning transaction and then receive `409`;
  clients must keep the documented refetch behavior.
- Session revocation is database-backed on every authenticated request by design.
  No security cache or refresh-token mechanism was added in this stage.
