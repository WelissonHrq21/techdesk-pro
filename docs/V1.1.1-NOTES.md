# TechDesk Pro v1.1.1 - Version/Metadata Reliability Notes

## Scope

v1.1.1 is a patch release for installer metadata and installed-version detection reliability. It does not add product features and does not change the planned v1.2.0 scope.

## Incident

A real clean install from the v1.1.0 RC2 installer on Ubuntu completed with healthy containers:

- `ghcr.io/welissonhrq21/techdesk-pro-api:1.1.0`
- `ghcr.io/welissonhrq21/techdesk-pro-frontend:1.1.0`

However, `/opt/techdesk-pro/techdesk status` run without `sudo` reported:

```text
Version: 1.0.0
```

The runtime had `/opt/techdesk-pro/VERSION` containing `1.1.0`, but the file was installed with mode `750 root:root`, so a normal user could not read it. The protected `.env` was correctly mode `600 root:root` and contained `TECHDESK_VERSION=1.1.0`. The expected public metadata file, `/opt/techdesk-pro/techdesk-installation.json`, was absent.

## Root Cause

The installer/status path combined three unsafe conditions:

1. `techdesk-installation.json` could be missing after an otherwise healthy install.
2. `VERSION` could be unreadable to non-root users because runtime copy permissions were too broad for public data files.
3. `current_version` silently fell back to `1.0.0` when metadata, `.env`, and `VERSION` were unavailable.

That fallback invented an installed version and could mislead status and upgrade decisions.

## Fix

- `current_version` now prefers metadata, then the public readable `VERSION` file.
- `current_version` no longer reads `.env` for read-only status and never falls back to `1.0.0`.
- If no reliable public source exists, status reports `UNKNOWN` with a diagnostic.
- Upgrade blocks when the current version is `UNKNOWN`.
- Install and upgrade only report success after metadata is written, chmodded, moved into place, and re-read successfully.
- Missing metadata is classified as a partial installation signal.
- Repair can rebuild missing metadata only when legacy sources agree:
  - `VERSION`
  - `TECHDESK_VERSION`
  - `TECHDESK_API_IMAGE` tag
  - `TECHDESK_FRONTEND_IMAGE` tag
- Repair blocks automatic metadata recovery when sources diverge.

## Permission Policy

Runtime file modes are now explicit:

- `techdesk`: `755`
- required `*.sh` scripts: `755`
- `VERSION`: `644`
- `.env.example`: `644`
- README files: `644`
- `docker-compose.yml`: `644`
- `nginx/default.conf`: `644`
- `.env`: `600`
- metadata: `644`
- logs and backups directories: `700`
- setup logs: `600`

`VERSION` and metadata contain no secrets. `.env` remains protected and is not required for non-root status.

## Expected Behaviors

- Metadata present and matching `VERSION`: status reports the metadata version.
- Metadata absent and `VERSION` readable: status reports the public `VERSION` value with a warning and partial-installation state.
- Metadata absent and `VERSION` unreadable: status reports `UNKNOWN`, never `1.0.0`.
- Metadata and `VERSION` mismatch: status warns and exits non-zero.
- Upgrade with current version `UNKNOWN`: blocked.
- Legacy v1.1.0 installation with missing metadata and coherent image/version sources: repair can reconstruct metadata without destroying data, secrets, or volumes.
- Legacy installation with divergent version sources: repair blocks with a diagnostic.

## Validation Notes

Automated setup regressions cover:

- the previous unreadable metadata/VERSION fallback scenario;
- read-only status without `.env`;
- metadata/VERSION mismatch;
- install finalization after metadata persistence;
- `VERSION` mode staying `644`;
- legacy metadata repair with coherent sources;
- repair block on divergent legacy sources;
- upgrade block on `UNKNOWN`;
- package archive file modes.

Full clean-install, reboot, image digest, and remote promotion validation must still be performed on the v1.1.1 RC candidate before final release.
